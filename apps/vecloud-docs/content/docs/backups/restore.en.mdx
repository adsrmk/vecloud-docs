Restoring involves choosing both a point in time and the parts you want to recover. This helps you match the restore to what happened on your website.

## Before you start

Check the domain in the topbar and choose a completed backup from before the problem. If needed, first save the current files and a database export to preserve recent data.

<Callout type="warning" title="Restoring overwrites existing content">
Changes made after the selected backup can be lost. Plan the restore outside busy hours and prevent new orders or other changes while it runs.
</Callout>

## Start the restore

With a suitable recovery point and its effects in mind, you can prepare the restore.

<Steps>
<Step>
### Open the recovery point

Go to **Backups** and choose **Restore** next to the backup. The **Backup details** modal shows the date, completion, storage and included components.

<PortalScreenshot name="backups" alt="Backup list showing the recovery point for example.test" caption="Start with a completed recovery point for the correct website. All data in these images is fictitious." />
</Step>
<Step>
### Check the contents

Check that website files were included successfully. Select the required **MariaDB databases** using the checkboxes. **Select all** selects every database shown.

The current restore modal includes available website files. It does not provide a file browser for choosing one individual file. Mailboxes may be listed in the details; that listing is not a separate restore selection.

<Callout>
Databases are not selected automatically. For a complete WordPress restore, explicitly select the database used by that installation. Without a database selection, this action restores only the available website files; database content such as posts, settings and orders stays at its current state.
</Callout>

<PortalScreenshot name="backup-restore" alt="Backup details with demo_wordpress explicitly selected" caption="Select the database used by this installation. It is not selected by default." />
</Step>
<Step>
### Confirm the action

Choose **Restore backup**. Read the confirmation and check the date and website again before confirming. A message that the restore has started means the request was accepted; it does not mean the website has finished restoring.

<PortalScreenshot name="backup-restore-confirm" alt="Final confirmation before restoring a backup" caption="Check the website and date again here. Cancel stops the action; only Restore now starts the restore." />
</Step>
<Step>
### Check your website

Let the restore finish before making further changes to the same website. Then test the homepage, administration area, forms and any shopping cart. Also check that the files and database belong to the same recovery point.
</Step>
</Steps>


## WordPress after a restore

An older database can replace recent posts, accounts and orders. Restore the appropriate files and database together when recovering a complete WordPress installation. Clear relevant caches afterwards if old pages still appear.

## An error or an uncertain outcome

Do not immediately start a second restore. Check the current website and available backup information first. Record the domain, selected date and error message for support. See [Backup troubleshooting](./troubleshooting.mdx).
