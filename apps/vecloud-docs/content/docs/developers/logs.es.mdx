Un registro resulta más útil cuando sabes qué evento estás investigando. Empieza por el problema y la hora, y consulta después la fuente de registro correspondiente.

## Registro de errores PHP

Abre **Domains → tu sitio → Developer tools → PHP**. **PHP error log** muestra el texto disponible y cuándo se obtuvo. Si es grande, puede mostrarse solo la parte final; el portal lo indica.

Anota la hora del fallo, repite una vez la acción si es seguro y vuelve a abrir los datos. Busca cerca de esa hora tipo de error, archivo y línea. **No PHP errors found** significa que el texto obtenido está vacío, no que todas las funciones estén bien.

## Elegir la fuente

| Problema | Dónde empezar |
| --- | --- |
| Fallo PHP o tras cambiar versión | PHP error log en Developer tools |
| Depuración WordPress | [Ajustes Debug](../wordpress/debug.mdx) y registro escrito por WordPress |
| Worker no arranca o falla | Registro de ese worker |
| Despliegue GitHub | Registro del despliegue en la integración |
| Traslado de servidor realizado por veCloud | Consulta a soporte sobre el progreso y el diagnóstico relevante |
| Importación SQL | Mensaje de importación y revisión de la base destino |

Puede existir una carpeta `logs` en **Files**. Su contenido depende del entorno. No presupongas acceso a todos los registros del servidor ni un visor independiente de accesos en el portal.

## Contactar con soporte

Indica sitio, función, error exacto, hora y acción anterior. Comparte solo el fragmento relevante. Elimina contraseñas, tokens, enlaces de sesión y datos personales antes de enviarlo.

Evita modificar varios ajustes a la vez para ocultar un error. Conserva valores originales, verifica tras cada cambio y utiliza una copia si necesitas recuperar datos. Un [gráfico de recursos](../performance/resources.mdx) puede relacionar un pico con la hora del fallo.
